# Report 2026-10-09: Release v1.0 — "Metal-Ready" 🎸

The desktop is complete, portable, and installable in one command.
This release marks the jump from VM to bare metal.

## What's in the box

**Desktop shell**
- Polybar pill bar with invisible top-row reserve bar
- Fullscreen-aware watcher v3 (hides only on real fullscreen; windows
  on the top strip never trigger it)
- Rofi: launcher (Super+Space), power menu, wallpaper picker with
  crossfade
- Hold-and-release Alt+Tab switcher (release Alt to commit, ~20ms) and
  classic Super+Tab switcher
- Plank dock (MaterialPill), picom compositor, update checker

**conky-glance widget**
- Date, weather (wttr.in, private local location), Spotify with
  clickable controls and progress
- Live 24-bar cava music spectrum while music plays
- Transparent, shadow-free, no icon-font glyphs (nothing renders as [])

**One-command install**
- `bash install.sh` does everything: package check (installs only
  missing, reports outdated, never upgrades silently), configs,
  xfconf settings (keybindings, stock panel off, margins), cava audio
  pinning, optional theme/icon extras
- Asks only for what's personal: weather location (stays in
  ~/.config/conky/location, never committed)
- Fully portable: no usernames or machine paths anywhere in the repo

## The journey (this release's highlights)

From the cava integration session through today: cava raw output was
binary by default; the awk bridge didn't split on ';'; the weather cache
used CPU-time instead of wall-clock and cached failures; the nerd-font
weather icon rendered as []; picom's shadow read as a border on the
transparent widget; the overlap watcher fired on any window touching
the top strip; XFCE keyboard shortcuts live under /commands/custom/,
not /custom/. Each fix is documented in the dated reports.

## Verification

- All scripts pass bash -n; install.sh is idempotent (re-runs skip
  installed packages and keep private files)
- Repo audit: zero hardcoded usernames/home paths; zip-code safety
  check in every push script; wallpapers and changes are the only data
  beyond configs

## Bare metal migration

    git clone https://github.com/lichtmeer/cachyOS-XFCE-dotfiles
    cd cachyOS-XFCE-dotfiles && bash install.sh

Then: log out/in, click the theme on (if the optional step was used),
clear saved sessions once, optionally theme LightDM. The verification
checklist in INSTALL.md walks the rest.

## Addendum: sandbox install-test — two real bugs found and fixed

The one-command installer was tested end-to-end in a sandbox with
stubbed system tools (pacman, xfconf-query, pactl) against empty home
directories, simulating fresh machines, plus re-runs for idempotency.

### What the test verified
- Package step: missing packages installed in one pacman call with
  --needed --noconfirm; installed ones skipped (verified with a
  partially-installed machine: only the missing ones were touched).
- All keybindings set, including Super+< (wallpaper switcher) and
  Super+Space (launcher).
- All config files land in place; the verify step passes; exit 0.
- Re-running asks nothing again and keeps private files.
- Weather question: asked once, saved with spaces/umlauts intact,
  empty answer = IP auto-detect, never asked again once saved.

### Bug 1: personal path still in the autostart step
The earlier audit script claimed to remove the `sed s|/home/userfolder|$HOME|g`
line from install.sh, but its sed command failed silently (delimiter
collision with the | characters in the pattern) and the line survived.
Replaced with a plain `cp` — the .desktop files are already portable.

### Bug 2: the weather question never existed
The docs promise the installer asks for a weather location "only if
~/.config/conky/location is missing" — but conky/install.sh contained
no such question. Fresh installs silently fell back to IP detection
and never saved the location. Added the question before the cava
pinning step; the file stays private and is never committed.

Both fixes were re-tested twice in the sandbox (second run applied the
exact patch blocks from the release script to a fresh clone):
location written on first run, kept on re-run, question not asked
again.

## Addendum: fresh-VM install test — root handling fixed

A real fresh CachyOS+XFCE VM tested the installer end to end. The run
started as `bash install.sh` was cancelled at the package step because
the sudo password prompt was mistaken for a login; the re-run as
`sudo ./install.sh` then broke everything: configs landed in /root,
the weather location was saved under /root, pactl could not reach the
user's audio server, and the keybinding step died ("Failed to init
libxfconf" — root has no user D-Bus session).

Fixes, all sandbox-tested before pushing:

1. Both installers abort with a clear message if run as root/sudo
   (`id -u` check). The only elevated part remains the internal
   `sudo pacman` call.
2. The installer prints an explanatory note right before the sudo
   password prompt appears, so it can't be mistaken for a login.
3. conky/install.sh tolerates a not-yet-running audio server
   (stderr silenced, friendly message, pinning deferred to next run).
4. README documents: plain `git clone` is anonymous on this public
   repo; `gh repo clone` demands a login even for public repos;
   never run the installer with sudo.

## Addendum: fresh-VM polish — panel popup and dead YAMIS repos

The fresh-VM campaign (installer run as a brand-new user on a real
CachyOS+XFCE VM) surfaced two remaining issues:

### 1. "Failed to restart the panel" popup during install
When the installer sets the panel list to zero, the running stock
panel notices its config change, tries to restart, and pops up a
GDBus error because nothing is left to activate. Harmless but
confusing. Fix: killall xfce4-panel BEFORE writing the setting — the
panel is stopped gracefully and never attempts its confused restart.
Verified on the VM afterwards: no panel running, setting stuck at 0.

### 2. YAMIS icon download failed on the VM
Both original GitHub repos (yeyushengfanw/yamis-icon-theme and
daniruixin/yamis-icon-theme) are gone — the accounts were deleted,
so both clone URLs fail. Fix: install from the original author's
source instead: Dirn's yet-another-monochrome-icon-set on Bitbucket
(dirn-typo/yet-another-monochrome-icon-set). The installer clones it
and copies the theme into ~/.icons/YAMIS/. Verified with a real
clone: index.theme present, ~6280 icons, theme registers as
"yet-another-monochrome-icon-set" in Appearance settings.

## Addendum: combined installer pass — compositor, keys, spotify gate, auto-theme, logout

One commit bundling everything the VM campaign surfaced:

1. **Compositor:** xfwm4's own compositor is switched off
   (/general/use_compositing = false) so picom owns the screen —
   two compositors fighting was only ever one crash away.
2. **Super+T:** alacritty had no keybinding; now bound alongside
   the other shortcuts.
3. **Super+Tab / Alt+Tab:** the real fix from the VM debugging. xfwm4
   keeps key->action MAPPINGS under /xfwm4/custom/; emptying the
   action values is not enough, and deleting the mappings falls back
   to factory defaults (which grab the keys). The installer now
   overwrites all three Tab mappings with 'empty' (unbound) so the
   rofi switchers finally receive the keys. Confirmed live on the VM.
4. **spotify-launcher:** removed from the silent package list; it now
   has its own permission question explaining why the glance widget
   wants it (music section talks to a Spotify player via playerctl).
   Skip prints the install command for later; already-installed stays
   silent.
5. **Auto-theme:** after the YAMIS/Orchis downloads the installer
   applies the settings itself via xfconf (GTK theme, icon theme,
   window-manager theme) — no manual clicking in Settings.
6. **Logout:** the installer ends by explaining WHY a fresh session is
   needed (autostart entries only start in a new session; keybindings,
   panel-off, compositor and theme are session settings) and asks
   "Log out NOW? [y/N]". Yes = clean logout after a 3-second warning.

### Testing
Sandbox runs with stubbed pacman/xfconf-query/pactl: full install
exit 0; spotify-y installs with the sudo note, spotify-n skips with
the hint; logout-y calls xfce4-session-logout, logout-n continues;
all six keybindings written in order; compositor=false, theme and
icon xfconf writes all logged.

## Addendum: Spotify question is asked on every run

### Symptom
On the VM, the Spotify permission question never appeared — because
spotify-launcher was already installed by an older installer version,
and the gate skipped the question entirely when it found any Spotify
present. The user wants to be asked every time, no exceptions.

### Root cause
The gate was a two-part condition: ask only when no spotify binary AND
no spotify-launcher package existed. An existing install silenced it.

### Fix
The question is now unconditional. If spotify-launcher is already
installed, the script says so before asking; a yes runs
pacman -S --needed (a no-op when present — never a reinstall), a no
prints the install-later command. The user decides on every run.

### Testing
Sandbox, stubbed pacman: installed+yes -> "already installed" note +
pacman runs harmlessly; not-installed+yes -> installs; no -> skips
with the hint. Question appears in all cases.

   installer sets one at random as the current desktop wallpaper (same

   the switcher needs a current wallpaper to start from.
2. **LightDM greeter themed:** if /etc/lightdm/lightdm-gtk-greeter.conf
   exists, the installer writes theme-name=Orchis-Dark and
   icon-theme-name=YAMIS into it (sudo note before the prompt). Other
   greeter = skip with a note.
3. **Readable step 9:** "Applying YAMIS icons + Orchis-Dark theme to

6. **Workspace margins:** top 0 (invisible bar rule — the watcher

install line carries --color=always; wallpaper picked and set;
margins written 0/55/55/15; greeter skipped cleanly when absent.

## Addendum: "YAMIS copy failed" on every re-run — .git was the culprit

### Symptom
From the second install onward, step 9 always reported
"YAMIS copy failed (skipped)". Harmless on machines that already had
the icons, but a fresh machine would have ended up without them.

### Root cause
The icon set is installed by cloning the Bitbucket repo and copying
its contents — including the hidden .git folder — into ~/.icons/YAMIS.
Git marks its internal pack files read-only. On every later run, cp
tries to overwrite those read-only files, gets "Permission denied",
and the copy is declared failed. Reproduced in the sandbox: first
copy OK, second copy fails with exactly those errors.

### Fix
The installer now removes the old ~/.icons/YAMIS first and copies the
set WITHOUT .git (tar --exclude=.git pipe). Re-runs are clean, and the
icon theme no longer ships a stray git repository.

### Testing
Live test against the real Bitbucket clone: fresh copy OK, immediate
re-copy OK (previously failing case), no .git in the target,
index.theme present. bash -n clean.
